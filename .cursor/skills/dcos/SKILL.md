# DCoS

DCoS（Design Concept System）は、Agentが裏側で使うデザイン方向性のファシリテーション手順。

ユーザーはDCoSの構成や用語を知らない前提で進める。ユーザーに仕組みを説明しすぎず、自然な対話で回答を引き出し、最後にそのまま使える生成用プロンプトを渡す。

## When To Use

ユーザーが次のように言ったら、このSkillを使う。

- デザインの方向性を決めたい
- DCoSで進めたい
- まだ作らず、方向性から整理したい
- いい感じにしたい
- 今っぽくしたい
- 無難にしたくない
- ムードボードを作りたい
- LPやUIを作りたいが雰囲気が決まっていない
- ブランド方向性を相談したい
- 既存サービスと違う感じにしたい
- 初回生成結果を見て、方向性を調整したい
- 生成結果が「方向性は良いが何か違う」と感じている

## User-Facing Rule

ユーザーには、原則として内部用語を出さない。

- Do not say: Direction Card, Design Concept Brief, DBS, DCS, Handoff Notes
- Say instead: 方向性案、デザインコンセプト、生成用プロンプト、評価の観点

例外: ユーザーがDCoSの仕組みそのものを質問した場合だけ、内部用語を短く説明する。

## Two Phases

DCoSには生成前と生成後の2つのフェーズがある。

```text
生成前:
質問 → 方向性案 → デザインコンセプト → 生成用プロンプト

生成後:
生成物 → ユーザー感想 → ズレの整理 → 維持/弱める/強める → 差分プロンプト

初稿以降:
差分プロンプト → 次の生成物 → 前回との差分確認 → 再調整 → 納得したら最終化
```

生成後フェーズでは、Agentが先に採点しすぎない。まずユーザーの感想を受け取る。
初稿以降は、ユーザーが納得するまでDCoS Iterationとして扱う。

## Default Response

DCoSが合う場面では、まずこう返す。ユーザーを待たせず、何が起きるかを短く伝える。

```text
いきなり作る前に、まずデザインの方向性を整理します。
いくつか質問するので、ラフに答えてください。
回答をもとに、方向性案を3つにまとめます。
```

## Modes

モード名は内部判断用。ユーザーに毎回説明しない。

### Quick

- 質問: 3つ
- 出力: 方向性案3つ
- 最終出力: 短いコンセプト、生成用プロンプト、確認観点

### Standard

通常の推奨モード。

- 質問: 5から7つ
- 出力: 方向性案3つ
- 最終出力: デザインコンセプト、やること、避けること、生成用プロンプト、確認観点

### Deep

本格的な上流設計に使う。

- 質問: 事業骨格、対象ユーザー、競合、避けたい既視感まで深掘り
- 出力: 方向性案、詳細なデザインコンセプト、ムードボード用プロンプト、UI/LP生成用プロンプト、評価観点

## Workflow

1. サービスやプロダクトの骨格を聞く。
2. 対象ユーザーと課題を聞く。
3. 使った後に持ってほしい体験感情を聞く。
4. 避けたい既視感を聞く。
5. 回答が曖昧なら、対立軸を提示して選んでもらう。
6. 回答が十分具体的なら、単一の仮方向性として短く要約する。
7. 回答が曖昧、または方向性の比較が必要なら、方向性案を3つ出して選んでもらう。
8. 選ばれた方向性、混合した方向性、または仮方向性を短く要約して確認する。
9. 確認できた方向性をデザインコンセプトへ統合する。
10. 最後に生成用プロンプト、制作ブリーフ、確認観点などユーザーの目的に合う出力へ変換する。

## First Questions

```text
まず、デザインを作る前に方向性を整理します。答えはラフで大丈夫です。

1. これは何のサービス / プロダクトですか？
2. 誰に使ってほしいですか？
3. その人は、今どんな課題や違和感を持っていますか？
4. 使った後に、どんな気持ちになってほしいですか？
5. 逆に、どんな見た目や印象は避けたいですか？
6. 近いと感じるサービス、遠ざけたいサービス、好きな雰囲気はありますか？

回答をもとに、方向性を整理します。十分具体的なら1案にまとめ、比較が必要なら3案に分けます。
```

## Handling Vague Answers

ユーザーの回答が「いい感じ」「今っぽい」「信頼できる」「楽しそう」のように抽象的な場合、すぐに結論を出さない。選びやすい対立軸へ分解する。

```text
「今っぽい」にもいくつか方向があります。

A. 先進的でシャープ
B. 人間味があって親しみやすい
C. 道具として使いやすそう
D. 文化や世界観がある

今回のサービスでは、どれが近いですか？
複数混ぜても大丈夫です。
```

## Reference Mixing

参考サイトや資料は、見た目のコピー元ではなく、考え方・構造・文脈を抽出する材料として扱う。

標準では、未確認URLを断定的に出さない。ユーザーがURLを提示した場合、またはAgentが実際に確認できる場合だけURLを使う。確認できない場合は、検索キーワードと見る観点を出す。

```text
参考をそのまま真似るのではなく、いくつかの文脈から考え方を分解して混ぜます。
今回は、写真の温度感、情報設計、タイポグラフィ、UIの明快さを別々に考えます。
```

方向性案や最終プロンプトでは、必要に応じて [reference-mixing.md](reference-mixing.md) の型を使う。

## Presenting Three Directions

3案は常に出すものではない。ユーザーの回答が具体的で、作る目的も明確な場合は、比較案を挟まず単一の仮方向性としてまとめてよい。

3案を出す条件:

- ユーザーが方向性に迷っている
- 避けたい印象はあるが、目指す印象が曖昧
- 複数の見せ方が同じくらい有効
- ユーザーが「案を見たい」「方向性を選びたい」と言っている

単一方向で進める条件:

- 対象ユーザー、課題、主要行動、目指す印象、避けたい印象が揃っている
- ユーザーがページ作成や制作ブリーフへ進みたがっている
- 3案選択が余計な往復になりそう

3案を出すときは、内部テンプレートを使いつつ、ユーザーには読みやすい候補として出す。

```markdown
方向性案を3つ出します。

## A. [案の名前]
[一言でいうと何か]

- 目指す印象:
- 色や形の方向:
- 向いている理由:
- 注意点:

## B. [案の名前]
...

## C. [案の名前]
...

どれが近いですか？
Aに近い / Bに近い / Cに近い / 混ぜたい / どれも違う、で答えてください。
```

## Confirming The Mixed Direction

ユーザーが1案を選んだり、2案以上を混ぜたいと言ったら、すぐに最終プロンプトへ行かない。まず採用方向を短くまとめて確認する。

```text
では、方向性はこうまとめます。

「[短いコンセプト名]」
[一文で方向性を説明する]

- 残す要素:
- 弱める要素:
- 避ける印象:

この方向で、今の目的に合う生成用プロンプトにまとめます。
```

ユーザーがすでに「その方向で進めて」「プロンプトまで作って」と言っている場合は、確認文を短く入れて、そのまま最終出力へ進んでよい。

## Output

DCoS Standard以上では、最後にこの形へまとめる。ここがユーザーにとっての成果物。

```markdown
# デザイン方向性まとめ

## 採用する方向性
[選ばれた方向性、または混合案]

## デザインコンセプト
[短いコンセプト名]

## なぜこの方向が合うか
[なぜその方向が合うか]

## ユーザーに持ってほしい感情
[ユーザーに持ってほしい感情]

## 見た目の方向性
[参照文脈、色、形、UI文法]

## やること
[やること]

## 避けること
[避けること]

## 今回作るプロンプト
[選んだ出力タイプと、その理由]

## 生成用プロンプト
[選んだ出力タイプに合わせたプロンプト]

## 出力を確認するときの観点
[生成結果を見るときのチェック項目]
```

確認観点は必ず3から6個入れる。方向性の良し悪しを判断できる問いにする。

例:

```text
- 狙った体験感情が出ているか
- 避けたい既視感に寄っていないか
- 主要ユーザーに合う温度感か
- 商品やサービスの特徴が見つけやすいか
- 次のUI/LP制作に使える具体性があるか
```

## Prompt Quality Rules

生成用プロンプトは、単なる雰囲気語で終わらせない。

- 最終プロンプトは、出力タイプに応じて [prompt-templates.md](prompt-templates.md) のテンプレートを使う。
- デフォルトでは複数種類のプロンプトを出さない。ユーザーの現在の目的に合う1種類を選ぶ。
- 出力前に「今回は何用のプロンプトを作るか」と「なぜそれを選ぶか」を短く書く。
- 複数種類が有効な場合は、最初に使うべき1つを明示する。追加分はユーザーが求めた場合だけ出す。
- ユーザーの回答が短い場合でも、対話で得た方向性から不足項目を補完して構造化する。
- 不明な項目は無理に断定せず、自然な仮置きとして書く。
- 何の画面/ビジュアルを作るかを明記する。
- 対象ユーザーと体験感情を入れる。
- 色、形、タイポグラフィ、UI部品の方向を入れる。
- 参照文脈は「何を借りるか」「何を真似しないか」まで書く。
- 避けたい既視感を入れる。
- 「やりすぎないための制御」を入れる。
- 実在ブランドの模倣指示にしない。
- ムードボード、LP/UI、バナーなど複数の出力を明示的に求められた場合は、それぞれ別プロンプトとして出す。

## After First Output

初回生成物を受け取った後は、評価者ではなく方向性の再調整ファシリテーターとして振る舞う。

### First Response

生成物だけが貼られた場合や、ユーザーの感想がまだ少ない場合は、まず感想を聞く。

```text
まず、この生成結果を見てどう感じましたか？
「ここは良い」「ここが違う」「もっとこうしたい」くらいのラフな感想で大丈夫です。
その感想をもとに、次の生成で維持する点・弱める点・強める点に整理します。
```

ユーザーがすでに感想を書いている場合は、追加質問を急がず、その感想を整理する。

### Post-Generation Workflow

1. 初回生成物を受け取る。
2. ユーザーの感想を受け取る。足りない場合は短く聞く。
3. 感想を「合っている点 / 違和感 / 追加したい方向」に分ける。
4. 生成前に決めた方向性やプロンプトと照合する。
5. 次に「維持する / 弱める / 強める」を整理する。
6. 必要ならデザインコンセプトや避けることを更新する。
7. 次の生成に使う差分プロンプトを作る。

### Adjustment Format

```markdown
## 生成結果を受けた調整

### 合っている点
- [維持したい良さ]

### 違和感
- [ユーザーが感じたズレ]

### 維持する
- [次の生成でも残す要素]

### 弱める
- [出すぎた要素]

### 強める
- [足りない要素]

### 更新した方向性
[必要な場合だけ、短く更新したコンセプトを書く]

### 差分プロンプト
[前回の方向性を保ちながら、次の生成で変える点だけを具体的に書く]
```

### Rules For Difference Prompts

差分プロンプトは、初回プロンプトを丸ごと捨てるものではない。

- まず維持する要素を書く。
- 次に弱める要素を書く。
- 次に強める要素を書く。
- ユーザーの言葉をできるだけ残す。
- 「もっと良く」ではなく、視覚的に操作できる言葉にする。
- 生成AIが過剰解釈しそうな要素には抑制条件を入れる。

## Iteration Loop

初稿以降は、すべてDCoS Iterationとして扱う。目的は、毎回ゼロから方向性を作り直すことではなく、ユーザーの納得に近づくように差分を小さく操作すること。

### Iteration Workflow

1. 新しい生成物を受け取る。
2. ユーザーの感想を聞く。すでに感想がある場合はそれを使う。
3. 前回から良くなった点を確認する。
4. まだ違う点を整理する。
5. 次に変える点を1から3個に絞る。
6. 必要なら、維持する / 弱める / 強めるを更新する。
7. 次の差分プロンプトを作る。
8. ユーザーが納得したら、最終方向性と最終生成プロンプトにまとめる。

### Iteration Format

```markdown
## Iteration [number]

### 前回から良くなった点
- [改善された点]

### まだ違う点
- [残っている違和感]

### 次に変える点
- [次回の生成で操作する点]

### 維持する
- [崩さない要素]

### 差分プロンプト
[次の生成で変える点だけを具体的に書く]
```

### Finalization

ユーザーが「これで良い」「かなり近い」「この方向で進めたい」と言ったら、反復を止めて最終化する。

```markdown
## 最終方向性
[確定した方向性]

## 最終生成プロンプト
[ムードボード、UI、LPなど次に使う最終プロンプト]

## 判断基準
- [今後の生成や実装で守る観点]
```

最終化が終わったら、必要に応じて Handoff to Yomogi を提案する。詳細は後述の `## Handoff to Yomogi` セクションを参照。

### Loop Guardrails

- 1回の反復で変える点は1から3個に絞る。
- 変える点が多すぎる場合は、優先順位をユーザーに聞く。
- 3回以上迷走している場合は、元の方向性案やデザインコンセプトに戻って照合する。
- 元の方向性自体が違うと分かった場合は、方向性案を再提示する。
- ユーザーの「良いと思う」部分は勝手に消さない。

## Major Direction Change

ユーザーが「方向性を大きく変えたい」「別案を見たい」「根本から違う気がする」と言った場合は、通常の差分調整を止める。これはイテレーションではなく、方向性の再分岐として扱う。

この場合、Agentはすぐに3から4個の新しい方向性案を出さない。方向転換したい背景には、ユーザーのゴールイメージがまだ言語化されていない、またはAgentがうまく引き出せていない可能性がある。

まずGoal Image Re-briefで、ユーザーの中にある「ピンと来ない理由」と「近づきたい方向」を深掘る。その後にだけ、新しい方向性案を出す。方向性案を出したらそこで必ず止まり、ユーザーが選択、混合、却下する前に生成用プロンプトを書いてはいけない。

### Goal Image Re-brief

方向転換時は、別案を出す前に次のように返す。

```text
別案を出す前に、少しゴールイメージを掘らせてください。
今の案がピンと来ないのは、方向そのものが違う可能性もありますが、
まだ「何に惹かれるか」が言語化できていない可能性もあります。
ラフでいいので、近い/遠いだけで答えてください。
```

質問は3から5問に絞る。ユーザーがすでに理由を書いている場合は、その内容を整理して不足分だけ聞く。

```text
1. 今の案で一番ピンと来なかったのは、色・写真・余白・言葉・情報量・世界観のどれですか？
2. 逆に、少しでも残してよい要素はありますか？
3. 「こうではない」は何ですか？
4. 近い感覚を、デザイン以外で例えると何ですか？ 音楽、店、雑誌、人、場所など。
5. 見た人に「何っぽい」と言われたら嬉しいですか？
```

回答を受けたら、まず「見えてきたゴールイメージ」を短く要約して確認する。

```text
いま見えてきたゴールイメージはこうです。

- 惹かれている方向:
- 避けたい方向:
- 残してよい要素:
- 新しく強めたい感覚:

この理解をもとに、方向性案を出します。
```

### Workflow

1. 方向転換したい背景を、すぐ案にせず受け止める。
2. ピンと来ない理由と、近づきたいゴールイメージを3から5問で深掘る。
3. 回答を「惹かれている方向 / 避けたい方向 / 残す要素 / 強めたい感覚」に整理する。
4. 見えてきたゴールイメージを要約して確認する。
5. その理解をもとに、新しい方向性案を3から4個出す。
6. 各案に「何が違うか」「向いている理由」「リスク」を添える。
7. 「どれが近いですか？混ぜたい案はありますか？」と聞く。
8. ユーザーの返答を待つ。
9. ユーザーが選んだ後にだけ、コンセプト化と生成用プロンプト作成へ進む。

### Stop Format

```markdown
方向性を大きく変える場合は、いったんゴールイメージを掘り直します。
この時点ではプロンプト化せず、まず「何がピンと来ないか」を整理します。

## まず確認したいこと
- 今の案で一番ピンと来なかったのはどこですか？
- 逆に、少しでも残してよい要素はありますか？
- デザイン以外で近い感覚を例えると何ですか？

回答をもとに、方向性案を出します。
```

深掘り後に方向性案を出す場合:

```markdown
見えてきたゴールイメージをもとに、方向性案を出します。
この時点ではプロンプト化せず、まず方向性を選びます。

## A. [方向性名]
- 何が違うか:
- 向いている理由:
- リスク:

## B. [方向性名]
- 何が違うか:
- 向いている理由:
- リスク:

## C. [方向性名]
- 何が違うか:
- 向いている理由:
- リスク:

どれが近いですか？
A/B/Cのどれか、または「AとCを混ぜたい」「全部違う」で答えてください。
```

### Hard Rule

- 方向転換の直後に、いきなり方向性案を出さない。まずGoal Image Re-briefを行う。
- ユーザーのゴールイメージが低解像度なまま、案の数だけ増やさない。
- 方向性案を出した同じ返答で、生成用プロンプトまで書かない。
- ユーザーの選択、混合、却下が返るまで収束しない。
- ユーザーが「その案で進めて」「プロンプトにして」と明示した後にだけプロンプト化する。

## Handoff to Yomogi

DCoSは方向性のファシリテーションを担うが、Yomogi本体（`brand.mdc` と `tokens/*.json`）への書き戻し経路も持つ。最終化（Finalization）まで進んだあと、ユーザーが「Yomogiに反映したい」「ブランド設定に書き戻したい」「トークンに反映してほしい」と言ったときに、書き戻し提案を出す。

### When To Hand Off

次のいずれかに該当したら Handoff モードへ移る。

- ユーザーが「Yomogiに反映」「ブランド設定に書き戻し」「トークン化」「実装に落としたい」と言った
- 最終化のあとに「次はどうしたら？」と聞かれた場合、選択肢として Handoff を提示する
- DCoS Iteration が3回以上回って方向性が安定し、ユーザーが採用を表明した

### Handoff Default Response

```text
方向性が確定したので、Yomogiのブランド設定とトークンに反映する書き戻し提案を出せます。
ファイルは直接書き換えず、提案として出します。採用可否は確認してから反映してください。
進めますか？
```

ユーザーが了承したら、`handoff-to-yomogi.md` のフォーマットに従って次の3つを順に出す。

1. **Brand Diff Proposal**: `brand.mdc` の該当セクションへの書き戻し提案（Markdown）
2. **Token Diff Proposal**: `tokens/*.json` への差分提案（JSONコードブロック）
3. **適用手順**: 反映 → `npm run build-all` → Storybook 目視 の流れ

### Handoff Hard Rules

- JSONを直接書き換えない。差分提案として Markdown のコードブロックで提示する。
- 採用可否はユーザーが判断する。AIは提案までを担当する。
- 新規プリミティブ（既存の `gray / blue / red / green / yellow / orange` 等にない色）の追加は影響が大きいので、必ずユーザー確認を取る。
- セマンティック層の差し替えで対応できる場合は、プリミティブ追加より差し替えを優先する。
- 適用後は `npm run build-all` の実行と Storybook での目視確認を必ず案内する。

詳細なフォーマットは [handoff-to-yomogi.md](handoff-to-yomogi.md) を参照。

# DIP

DIP（Design Iteration Protocol）は、レビュー結果を「今回どう直すか」に変換する手順。チェックが診断なら、DIP は治療順を決める役。

ユーザーには通常「改善案」「今回の修正案」「直し方」と呼ぶ。

## Inputs

- チェック結果、`npm run dcs-report` の結果、またはユーザーの違和感
- 対象HTML/CSS
- DBSブリーフ、DCoS方向性、`brand.mdc` があるなら優先して参照

レビュー結果が無い場合は、必要に応じてチェックを先に実行する。

## Workflow

1. チェック結果とユーザーフィードバックの両方を確認する。ユーザーにはDCS/DIPなどの略語理解を求めない。フィードバックが無い場合は、先に「見た目や使い心地で気になる点はありますか？」と短く確認する。ただしユーザーが即修正を求めている場合は、仮置きして進めてよい。
2. 指摘を4種類に分ける。
   - 重大違反: トークン、構造、a11y、コントラスト、生成場所
   - 情報構造: 見出し階層、情報順、CTA、主役不在
   - 視覚調整: 余白、サイズ、色、境界、密度、強調度
   - 表現調整: コピー、トーン、ブランドらしさ、避けたい既視感
3. 重大違反がある場合は最優先する。重大違反がない場合は、ユーザーフィードバックを主材料にして、情報構造・視線誘導・表現調整へ翻訳する。
4. 視覚調整は、主役とCTAに関係するものだけ先に触る。
5. コピーや細部の装飾は、構造が直ってから扱う。ただしユーザーの違和感がコピーの明確さにある場合は、heroやCTA周辺など範囲を限定して扱う。
6. 今回の修正の完了条件を明記する。
7. 必要ならそのまま実装するか、修正プロンプトを出す。

## Scope Planning

1回の修正に詰め込みすぎない。

- **今回の修正**: 重大違反、見出し階層、主役、CTAなど、最初に直すべき範囲
- **次回以降の修正**: 余白、密度、コンポーネント化、レスポンシブ
- **仕上げ**: コピー、ブランド表現、微細な視覚演出

ユーザーが即修正を求めている場合は、今回の修正範囲から実装する。相談だけなら、実装指示と優先順位を出す。

## Output Format

```markdown
# 改善案

## 今回直す範囲
[範囲と理由]

## 直すこと
1. [具体的な修正]
2. [具体的な修正]
3. [具体的な修正]

## 今回触らないこと
- [後回しにするもの]

## 実装指示
[AIまたは実装者に渡せる指示]

## 完了条件
- [再チェックで確認する項目]
- [見た目や体験の確認項目]
```

## Repair Prompt Pattern

```text
次のYomogiページを改善してください。

今回の修正範囲:
[範囲]

必ず直すこと:
[チェックで出た測定可能な指摘]

見た目の方針:
[DCoS/DBSから維持する方向性]

制約:
- px / hex / rgba の直書きをしない
- 実在する Yomogi トークンだけ使う
- 既存コンポーネントを優先する
- 新規ページは pages/generated/ 配下

完了条件:
[再チェック条件]
```

## Rules

- すべてを一度に直そうとしない。
- チェックで出た測定可能な違反を、好みの問題として後回しにしない。
- チェック結果だけで改善案を決めない。ユーザーの見た目・体験へのフィードバックも材料にする。
- チェックに重大違反がない場合は、軽微な警告を過大視しない。
- ユーザー向け出力では、DCS/DIPという略語を使わない。「チェック結果」「改善案」「今回の修正案」「直し方」と書く。
- ユーザー向け出力では「DIP手順に沿って」「DCS上の」のような内部手順名を出さない。
- ユーザーが「違和感」だけを述べた場合は、構造、主役、密度、トーンのどこに属するかへ翻訳する。
- 原則やトークン体系を壊す要望は、目的を保ったまま別の表現へ置き換える。
